# RabbitMQ и общая очередь AI — проверка 8 ноября 2026

Проверено текущее рабочее дерево на Windows. Миграция реализована и проверена
локально; production не развёртывался. Даты логов UTC могут показывать 7 ноября.
Изменения других задач в рабочем дереве сохранены.

## Что реализовано

- BullMQ заменён транспортом `@openfacto/queue` на amqplib. Redis больше не нужен
  для очередей и readiness. Старые Redis volumes не удалялись.
- Telegram и Playground используют одну физическую очередь RabbitMQ `ai.questions`.
  Общий лимит параллельной обработки задаёт `WORKER_CONCURRENCY` внутри backend.
  Обработчики работают в процессе NestJS; `apps/worker` остаётся библиотекой.
- В RabbitMQ передаются тип и ID задания. PostgreSQL хранит ввод, состояние,
  попытки и результат. Миграции `0010_async_playground` и `0011_queue_dispatches`
  применены к тестовой БД. Повторное применение миграций проходит.
- Playground принимает POST с ответом 202, затем UI опрашивает GET статуса.
  Повтор с тем же ID и вводом не создаёт новое задание; другой ввод с тем же ID
  отклоняется. После таймаута UI повторно использует исходный ID.
- Транспорт использует persistent messages, durable queues, publisher confirms,
  manual ack, ограниченные очереди и dead-letter queues. SQL leases и sweep
  восстанавливают незавершённую работу. Резервирование отправки предотвращает
  постоянную публикацию дублей и блокирование последующих задач первыми 50.
- Проверки организации, мероприятия, роли и актуальности источников выполняются
  при обработке и выдаче результата. Отзыв доступа или источника учитывается.
- Загрузка документов, оценки и доставка сообщений имеют отдельные очереди.
  Обновлены Compose, CI, readiness, примеры окружения, архитектура и runbook.

Проверки выполнялись с настоящим локальным RabbitMQ. Проверены redelivery,
переподключение и восстановление, дубли Telegram/Playground, истечение leases,
исчерпание попыток, 61 ожидающее задание без starvation и освобождение dispatch
после неуспешной публикации. При остановке зависимости readiness менялась
200 → 503 → 200, liveness оставалась доступна. Сообщение RabbitMQ, записи
PostgreSQL, векторы Qdrant и объект S3 пережили пересоздание контейнеров без
удаления volumes.

В ходе проверки исправлены два устаревших тестовых ожидания: браузерный locator
стал выбирать результат ответа, поскольку тот же текст есть в истории; replay
проверяет содержимое и оплаченные вызовы без требования одинаковой длительности
повторного исполнения. Оба затронутых теста повторно прошли. Полный браузерный
прогон сначала дал 2/3; исправленный третий сценарий отдельно дал 1/1.

Turbo выводил предупреждения о недоступности Git dirty hash и отсутствии файлов
coverage для тестовых задач; команды завершились успешно. Это не ошибки тестов.

## Как повторить

Из корня проекта после установки зависимостей:

```powershell
pnpm check
pnpm check:spa
pnpm python:test
```

Для интеграций настройте серверный `.env` и поднимите отдельную тестовую
инфраструктуру по [RUNBOOK](RUNBOOK.md), затем:

```powershell
pnpm db:migrate
pnpm test:integration
pnpm test:e2e
pnpm python:test:integration
pnpm verify:local
```

`verify:local` намеренно останавливает и пересоздаёт контейнеры указанного Compose
проекта. Выполняйте его на тестовой инфраструктуре без параллельно работающего
backend над той же БД. Интеграционные пакеты запускаются последовательно, поскольку
их диспетчеры выбирают задания из общей тестовой БД. Проверки с реальной AI-моделью
требуют настроенного provider и расходуют его квоту.

Браузерные проверки находятся в `apps/mini-app/test/`; им нужны запущенный backend,
Vite и Chrome. Переменные для каждого сценария заданы в начале соответствующего
файла. Проверки PDF и semantic retrieval находятся в `apps/worker/test/` и требуют
S3, Qdrant, PDF worker и настроенного embedding endpoint.

Использованный Compose-проект: `openfacto-qa-20261107`; PostgreSQL 55432,
RabbitMQ 5673, management 15673, Qdrant 56333, S3 59000. Локальный кабинет оставлен
на http://127.0.0.1:55173, API на http://127.0.0.1:53000 и использует эту тестовую
инфраструктуру. Корневой `.env` для обычного запуска настроен на RabbitMQ 5672.

## Границы проверки

- Настоящий публичный Telegram webhook и отправка сообщения реальному участнику
  не проверялись: transport/API тесты используют контролируемые Telegram fixtures.
- Это функциональная локальная проверка, без нагрузочного теста и проверки HA
  кластера RabbitMQ. Доставка допускает повторы; бизнес-обработчики используют SQL
  claims и идемпотентность. Exactly-once для внешней отправки не заявляется.
- Незавершённое Playground-задание сохраняется в БД после перезагрузки страницы,
  но автоматическое восстановление UI через sessionStorage не реализовано.
- Новая SPA и backend должны обновляться вместе: старый синхронный контракт
  Playground заменён на POST 202 + GET статуса.
- Результаты относятся к перечисленным тестам и данным, а не к гарантии понимания
  любого разговорного или неполного вопроса.
